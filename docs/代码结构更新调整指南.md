# StudyAgent-client 代码结构更新与调整指南

## 1. 调整目标

本次调整不是简单地“把大文件拆小”，而是按照业务领域重新组织代码，降低以下风险：

- 单个文件职责过多，修改一个功能容易影响其他模块。
- Rust 命令层、业务逻辑、文件读写、权限校验混在一起。
- Vue 页面同时承担数据请求、状态管理、业务计算、组件渲染和样式。
- 多人协作时容易产生大量冲突。
- 测试只能覆盖整体流程，难以单独验证领域逻辑。
- 后续权限收敛、错误处理和接口版本管理困难。

本次重构不包含依赖大版本升级，不迁移到 TS7、Vite8、Pinia4 或 Vue Router 5。现有稳定组合应保持不变。

stdio MCP 当前仍未完成，本次只保留现有入口并进行边界隔离，不扩展其业务范围。

---

## 2. 当前代码规模

当前主要超大文件：

| 文件 | 当前规模 | 主要问题 |
|---|---:|---|
| src-tauri/src/api/commands.rs | 约 4236 行 | 所有 Tauri 命令集中在一个文件 |
| src-tauri/src/core/planner.rs | 约 3939 行 | 计划生成、解析、约束、补救逻辑混合 |
| src/views/SettingsView.vue | 约 3959 行 | 设置、Provider、MCP、备份、更新、外观全部混合 |
| src/views/DebugView.vue | 约 2494 行 | 调试、日志、Provider、AI 用量、数据检查混合 |
| src/views/DashboardView.vue | 约 2222 行 | 首页数据加载、简报、昨日复盘、周计划、动画全部混合 |

建议目标：

- 单个路由页面控制在 300～600 行以内。
- 单个领域组件控制在 300～500 行以内。
- 单个 Rust 命令模块控制在 300～600 行以内。
- 纯解析器、计算器、格式化器控制在 100～300 行以内。
- 业务服务可以较大，但必须职责单一并有独立测试。

## 5. planner.rs 拆分方案

当前 planner.rs 同时承担 AI 请求、Prompt、计划生成、重新生成、排除日期、休息日、历史完成情况、解析、fallback、一致性校验和持久化。

建议拆成：

~~~text
core/planning/
├─ mod.rs
├─ service.rs
├─ generation.rs
├─ regeneration.rs
├─ prompts.rs
├─ parsing.rs
├─ constraints.rs
├─ fallback.rs
├─ consistency.rs
├─ scheduling.rs
└─ persistence.rs
~~~

拆分顺序：

1. 先提取 weighted_spread、subject_task_budget、memory_curve_review_items、休息日/排除日约束等纯函数。
2. 再提取 Prompt 构建函数。
3. 再提取 JSON 解析和一致性修正。
4. 最后保留一个薄的 PlanningService 负责串联异步流程。

## 9. API 与 Store 调整原则

现有 src/api/index.ts 可以继续作为兼容层，但新代码应逐步使用领域 API：

~~~text
features/planning/api.ts
features/review/api.ts
features/focus/api.ts
features/textbooks/api.ts
features/providers/api.ts
features/updates/api.ts
~~~

推荐调用链：

~~~text
组件 → composable → store → feature api → api/index.ts → Tauri
~~~

组件不应直接调用 Tauri invoke。Store 只负责保存领域状态、调用 API、管理 loading/error 和暴露领域 action。

跨领域调用应通过公开 API 或 Store selector，不要直接访问另一个 feature 的内部文件。

## 10. 类型组织原则

领域类型放入对应 feature：

~~~text
features/planning/types.ts
features/review/types.ts
features/focus/types.ts
features/providers/types.ts
features/updates/types.ts
~~~

只有真正跨领域共享的类型才放在 src/types/。Rust 侧应区分领域内部模型、Tauri Command DTO、前端返回 DTO 和持久化文件模型，避免前端直接依赖 Rust 内部结构的全部字段。

## 11. 安全与权限边界

重构后必须保持以下规则：

1. 所有路径参数经过统一校验。
2. Debug 文件读取继续使用允许目录白名单。
3. 更新下载继续校验 URL、文件名和 SHA-256。
4. 不在持有全局状态锁时执行长时间网络请求。
5. AI Provider API Key 不写入日志或错误字符串。
6. Settings 命令不直接拥有 Debug 或 Update 的内部权限。
7. MCP 命令单独控制能力，不通过通用命令暴露任意工具调用。
8. 前端不自行拼接敏感路径或更新安装路径。

建议为领域服务定义领域错误，例如：

~~~rust
pub enum PlanningError {
    InvalidDate,
    InvalidResponse,
    Storage(String),
    Ai(String),
}
~~~

再由命令层统一转换为前端可识别的错误结构。

## 12. 推荐迁移顺序

### 阶段 0：建立基线

- 记录 pnpm type-check、pnpm build、pnpm test、cargo test 结果。
- 建立命令清单和页面职责清单。
- 不修改业务行为。

### 阶段 1：拆 Rust 命令入口

- 新建 api/commands/。
- 按领域移动命令函数。
- 保持函数名和参数不变。
- 只调整模块导出和 Tauri 注册。

### 阶段 2：拆 Planner 纯逻辑

- 先移动解析器、约束、fallback 和版本计算等纯函数。
- 给纯函数补充单元测试。
- 最后拆 Prompt 和异步编排。

### 阶段 3：拆 SettingsView

推荐顺序：外观设置 → 备份和数据目录 → Provider → MCP → 教材配置 → 更新和通用设置。

### 阶段 4：拆 DebugView

先提取格式化器和测试状态，再提取各个调试面板。

### 阶段 5：拆 DashboardView

先抽取数据加载和计算 composable，再拆 UI 卡片。

### 阶段 6：统一 API 与 Store 边界

- 页面中移除直接 API 调用。
- Store action 统一返回错误。
- 清理重复 loading/error 状态。
- 补充跨领域 API 测试。

### 阶段 7：清理兼容层

- 删除旧文件中的 re-export。
- 删除重复函数和无用 import。
- 更新目录文档和贡献指南。

## 13. PR 拆分建议

不要一次性重写全部目录，建议拆成多个小 PR：

1. refactor: introduce domain feature boundaries
2. refactor: split tauri command modules
3. refactor: split planner pure logic
4. refactor: extract settings sections
5. refactor: extract debug panels
6. refactor: extract dashboard components
7. test: add domain service coverage
8. chore: remove legacy compatibility exports

每个 PR 应满足：

- 只处理一个领域。
- 不进行大规模格式化。
- 不升级框架依赖。
- 不同时改 UI 和后端业务规则。
- 提供迁移前后行为说明。
- 至少通过类型检查和构建。
- 纯逻辑变更必须有单元测试。

## 14. 完成标准

重构完成后应满足：

- commands.rs 不再承载所有命令，或仅保留兼容导出。
- planner.rs 拆成多个 planning 子模块。
- Settings、Debug、Dashboard 页面只负责页面组合。
- 页面组件不直接调用 Tauri invoke。
- 每个 feature 有明确的公开入口。
- Feature 之间没有循环依赖。
- 共享目录没有反向依赖业务 feature。
- 路径校验、更新校验、API Key 处理规则保持不变。
- stdio MCP 仍处于隔离状态，不影响其他 Provider。
- pnpm type-check、pnpm build、pnpm test、cargo test 通过。
- Planner、Textbook Search、Update Verifier 具有独立单元测试。
- 同一功能修改不再需要同时编辑多个超大文件。

最终目标不是文件数量越多越好，而是让每个模块拥有清晰的业务边界，并且能够独立测试、独立演进、独立控制权限。
